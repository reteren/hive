### Measurement notes

The snapshot figures above are **measured** with Node 24.11.1 / Vitest 3.2.7 using the actual `makeSnapshot` and `isDirty` implementations, exposed only in a temporary Vitest transform. The synthetic board had 1,000 or 10,000 ordinary notes with short text, no links/zones, three warmups, then 20 samples at 1,000 or 10 at 10,000; medians are reported. It excludes reactive scheduling, IPC, Rust saves, and disk I/O, and richer production nodes will cost more. The harness is under `%LOCALAPPDATA%\Temp\claude\d42_e\`.

All other 10k costs in the table are **estimates from the loops and file operations cited**, not timings. In particular, the 100M MCP counts assume 10,000 links and a sparse `linkedTo` match; actual early exits vary with link order.

## Culling / LOD contract

Persistence must receive the **complete board**, regardless of viewport; culling must never omit off-screen objects from save, backup, MCP search, or change tracking. Its useful shared contract is a monotonically increasing board revision and a complete dirty-ID set captured atomically with that revision, including object additions/deletions and project-level collection changes.

For MCP `bbox` queries, the useful service is a global board-unit spatial query: input is a caller-provided rectangle (or viewport rectangle), optional overscan, and board revision; output is every matching ID/bounds plus the revision. Update it on add/delete/move/resize and zone geometry changes. A visible-set/LOD service may additionally return viewport-intersecting IDs and a zoom bucket once per animation frame, but semantic MCP list/search and persistence must opt into the global index rather than use the visible subset.

## Quick wins (each intended to stay within 30 changed lines)

- In `nodes.list`, build the set of IDs linked to `linkedTo` once, then filter with `Set.has`; this removes the nested link scan with little behavior risk.
- Add a one-pass `membersByZone` helper and use it in `board.overview`; preserve the existing `membershipFor` tie rules while avoiding one board scan per zone.
- In `board_watch`, hash only tile paths present in the debounced event batch and update/remove those entries in `DRAWING_KNOWN`; retain full scans for startup/recovery.

## Structural changes

- Dirty-ID/revision based frontend snapshots and a matching per-object Rust save plan.
- Incremental watcher reconciliation, with conservative full-load fallback for ambiguous Git event batches.
- Reusable global spatial, adjacency, name, and search indexes shared by MCP and UI consumers.
- Reuse project-load note fingerprints; consider lazy Markdown bodies only with a corresponding search/content-loading contract.
- Incremental backup manifests and explicit semantics for project-open snapshots.

## Open questions

- Should opening a project always create a new snapshot, or only when its fingerprint differs from the latest snapshot?
- For large projects, should the default automatic backup interval remain 30 minutes, and are incremental snapshots acceptable if restore still produces a complete project?
- Can the frontend's project-load contract move to lazy Markdown bodies, or must every body be resident immediately for current search/render behavior?
- Which MCP operations are expected to query the entire board versus a caller-supplied bounding box? Generic `nodes.list` and `search` currently have global semantics.
