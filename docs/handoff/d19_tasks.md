Same guarantees as the current daily path: one fire per occurrence, key = local date + time, missed occurrences coalesce into one overlate fire, and nextDueAt returns the next allowed day. Without a rule, behaviour is exactly as today (date → once, null → daily). validateSchedule rejects: weekly with an empty/invalid days list, monthly day outside 1..31, yearly with an invalid month/day (29 Feb is valid).

It covers "at" schedules (once / daily / rules) and "interval" schedules in calendar mode, projected from runtime.intervalStartedAt (repeat → every step, otherwise one). App/active intervals return [] because they can't be projected. It works regardless of `enabled` — the Calendar decides whether to show disabled nodes. The Calendar task depends on this; land it FIRST, as its own commit, and notify the coordinator.

The existing date field means "starts on" when a rule is set. Map the existing states: once = date set, no rule; daily = date null, no rule. Weekly → a row of 7 compact toggle chips (Mo Tu We Th Fr Sa Su; the stored numbers are 0 = Sunday). Monthly → a day number 1..31 input with a hint "31 = last day of short months". Yearly → month + day. Every change goes through the existing undoable time-edit path (one Undo step per change) and restarts the runtime like the other schedule edits.
